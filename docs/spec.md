# Nextomic Builder: Product Spec

Nextomic is a self-hosted visual builder for reactive, responsive, dynamic, complex websites and web apps. Output targets: Next.js and Astro. It combines the best of Bricks Builder (classes, IDs, design system, themes, dynamic data), FlutterFlow (queries, app state, action flows, authentication, integrations), and Instatic (self-hosted, own database, media manager).

Design sources are in `blueprint/` (see `ui-reference.md` for the index, coverage, and the rules for following them).

## Principles

1. Everything is JSON. Pages, templates, themes, classes, variables, actions, and queries are data; the renderer and exporter produce code.
2. Platform and built apps are separate. The platform runs on its own Postgres + Better Auth. Supabase/REST are integrations for built apps. Builder auth and built-app auth are different systems.
3. Output has no builder lock-in. Exported projects run anywhere with no Nextomic server, and still contain `nextomic/project.json` so the builder can re-import and edit them.
4. One source of truth per concern: schema in `packages/schema`, builder UI tokens in `blueprint/tokens.json`, built-site design in project data (variables, classes, themes).
5. Never mix builder UI styling with built-site styling. The builder UI uses HeroUI + Tailwind. Built sites use the generated Nextomic CSS framework and the project's themes (see `design-system.md`).
6. Dynamic data works everywhere (see `elements.md`).
7. Runtime: Bun primary, Node (latest LTS) supported. CI runs tests on both.
8. Follow the designs. Ask when something is not designed.

## Decisions log

- Builder DB: Postgres + Drizzle. Builder auth: Better Auth.
- Builder UI: HeroUI + Tailwind, because the supplied Figma design system is the HeroUI kit (token names, components, and variants match). This replaces the earlier plan to use shadcn/ui for the builder UI. Built sites still get a shadcn-like look through the generated CSS framework (plain CSS variables and classes, no Tailwind or HeroUI needed in output). Confirm with the owner if shadcn/ui must be used instead.
- Builder UI is dark-first; light mode supported via the light tokens.
- SMTP (2026-11-08, owner decision): SMTP comes only from the `SMTP_*` variables in Docker Compose / Dokploy, for the builder and for built apps. The saved-accounts screen built earlier the same day was removed (migration `0007_env_smtp.sql` drops `smtp_accounts` and `email_templates`). Platform email goes through the queue in `server/mail/*`. Email verification is enforced only when `SMTP_HOST` is set at start.
- Auth origin (2026-11-08): Better Auth gets `baseURL` and `trustedOrigins` explicitly from `BETTER_AUTH_URL` (normalized to its origin) plus optional `BETTER_AUTH_TRUSTED_ORIGINS`, so behind Traefik links and the origin check use the public address.
- Profile images (2026-11-08): stored through the storage adapter at `avatars/<userId>/<random>.<ext>`, served by `/avatars/<userId>/<file>`, link saved in `user.image`. Avatars without an image show the first letter of the name.
- Auth page look (sign-in, sign-up, forgot/reset password) is NOT in the Figma frames; it follows the inputs of `pages/editor-supabase.png` (pill inputs, 2px outline, label above, outlined rounded surfaces) with white-shade buttons (`default-800` in dark, inverts in light). Shared controls: `components/ui/controls.tsx` (rules in `ui-reference.md` section 3); auth chrome in `components/auth/auth-ui.tsx`.
- Runtime/package manager: Bun workspaces. Verify the Next.js production server under Bun; if any issue, run Next under Node and keep Bun for tooling, tests, and scripts. Do not block progress on this; record the result here.
- Next.js production server verified under Bun (2026-11-06): the `oven/bun:1` image runs `next start` and the signup-to-project e2e passes against it. No need to fall back to Node.
- Platform Postgres is `postgres:18-alpine`, defined in the same `docker-compose.yml` as the app and a one-shot `migrate` service, so Dokploy deploys one Compose stack. Volume mounts at `/var/lib/postgresql` (Postgres 18+ layout). See `dokploy/README.md`.
- Element IDs: `nxtomc-` + 8 random chars (`a-z0-9`), generated when "Generate element ID automatically" is on in project settings.
- Importing means re-importing Nextomic-made projects (`.nextomic.zip` or the `nextomic/project.json` inside an exported site). Importing arbitrary third-party sites is out of scope.
- Theme = Bricks-like style set chosen per page by conditions; color mode = light/dark inside a theme. Templates (header, footer, 404 first) also apply by conditions. Details in `templates-and-themes.md`.
- Dynamic data is available on every element prop, attribute, style value, and action parameter (opt-outs need a written reason in the registry).
- Auth actions are available on every element, not only forms. Built-app providers: Supabase and Custom API. Default session storage: httpOnly cookies set by generated server routes.
- REST editor syntax follows the designs: `<variable>` in JSON bodies, `[variable]` in headers and URLs. Dynamic data tokens elsewhere use `{{ }}`.
- Media page and Action flow editor and App Settings: replicate the supplied inspiration structures with Nextomic styling.
- Breakpoints are user-defined per project (create and manage from the three-dots menu next to the breakpoint switcher). Defaults: desktop (base), tablet (and below 768px), mobile (and below 414px). Kinds: base, "and below" (max-width), "and above" (min-width). Maximum 8.
- Editor top bar and panels are specified in `ui-reference.md` 4.3. The moon/sun switch previews the built site in light or dark; the builder UI's own color mode is a user setting. The Navigator panel holds only the page's elements; pages and templates are chosen from the page select.
- Left rail: Navigator, State Management, Media, Supabase, API Data, Design System, Custom Codes, Git Connection, Version History, plus App Settings at the bottom. Supabase and API Data are separate items; there is no Data Management group.
- Right panel with nothing selected shows page options: Page Parameters, Route Settings (with Requires Authentication), and Page State Variables. With an element selected it shows the Element, Design, and Action tabs.
- Publishing applies to the whole project (all changed pages, templates, themes together), with a check dialog first. Save stores a version snapshot without publishing. Awaiting owner confirmation.
- Builder icons come from Iconify-bundled sets (Streamline, Lineicons, Phosphor, Fluent, others) with Google Material Symbols as a last-resort fallback; licenses are tracked per set.
- App state can persist in the visitor's browser (local storage by default; cookie optional) until logout or site data is cleared. Page state never persists. Constants are read-only. See `dynamic-data-and-actions.md` section 5.
- The dashboard body (KPIs, charts, activity) is designed in-house and built last, after owner approval of a proposal.
- Built-site fonts and icons: managed in Design System > Fonts & Icons. Fonts are self-hosted by default (no runtime calls to font CDNs). Icon libraries default to inline SVG output with icon-font output as an option, and custom icon fonts and SVG sets can be imported. Licenses and attribution are tracked. Details in `fonts-and-icons.md`.
- Reusable components are deferred (Phase 14); the schema reserves `componentInstance`.

The server keeps the newest N snapshots per page and skips snapshots while the switch is off. Elements without an automatic ID get one when a page loads with the setting on (they are marked unsaved).

## Glossary

Project, Page, Template, Theme, Color mode, Element (node), Class, Variable, Query, Loop, Binding, Condition, Action flow, Connector, Auth provider, Dynamic data, Scope.

- Canvas view: plain mouse wheel zooms around the cursor (0.1x to 4x), Shift+wheel pans, holding the middle button drags. The iframe forwards wheel and middle-button events to the editor through validated postMessage. The frame grows to the page height, so the canvas pans instead of scrolling inside the iframe. Rotate swaps a non-base breakpoint to landscape width (preview only).
- Dragging onto the canvas: while a drag is active a shield covers the iframe; the editor sends pointer coordinates, the canvas hit-tests with elementFromPoint and draws the drop marker, then the drop uses the last reported target. Nothing from the iframe can read the builder.
- Exactly one home page per project: saving a page with isHome set clears the flag on all others in the same transaction.
- Publish is a joined split control. Publish puts every page with includeInPublish live as a snapshot (pages.published_snapshot, projects.published_at/published_settings); the arrow holds Save, Preview draft, Version history and Unpublish. Public URL: /site/<projectId>/<route> reads ONLY snapshots with no session. Drafts are only served by /preview/<projectId> to signed-in project members. Pages with requiresAuth are not served publicly until end-user auth exists.
- Breakpoint order is derived from width, never set by hand: larger-than-base ("up") widest first, then the base, then "down" widest first (sortBreakpoints in packages/schema). The manager has no reorder buttons and re-sorts when a width or kind is settled.
- "Generate element ID automatically" is an App Settings option (project-wide), not a per-element switch.
- Element identity input: one field for classes and the ID. Plain text is a class, #text is the ID. Classes are stored by name in classIds until the class manager (Phase 2) and render as the class attribute.
- Fields get a bolt: Element-tab fields insert {{param.x}} / {{state.x}} tokens (MixedText); design-value bolts are shown disabled until the dynamic data phase.
- Dropdowns are HeroUI Select via SelectField. Inside a scrolling modal React Aria closes the list on the stray scroll that opening causes, so SelectField ignores scroll for 400 ms after opening.
- Saving is explicit (Save, Ctrl+S, Publish); there is no autosave. Unsaved edits are lost on refresh, switching pages warns, and preview and the public site show only saved or published content. The Publish control shows a status dot: red unsaved, orange saved draft, green published; Publish becomes a disabled "Published" when the saved draft equals what is live (server-side comparison).
- Canvas, preview and published pages share one base stylesheet (`BASE_CSS` in `packages/renderer`), so the three look the same. The element menu (right-click) adds a `hidden` flag on element nodes (hidden in editor and output).
- CSS text editing uses PostCSS (`packages/schema/src/css-text.ts`); a rule maps to the StyleMap only when its selector is exactly the target plus an optional pseudo state, everything else is kept in `raw` and output verbatim. Code fields use syntax colors (own tokenizer, no dependency).
- Class and variable renames/deletes also rewrite the other saved pages on the server (version bump), then the open page is saved in the same step. Classes are still stored by name. Variables live in `ProjectSettings.variables` and are output as `:root{--nxt-*}`.
- Pseudo states are chips beside the class chips (single click). An element ID cannot be removed while "Generate element ID automatically" is on, and it is active whenever no class is selected.
- Element panel (Phase 2): the ID field is read-only until the pencil is pressed; class chips activate on double click only and everything not active is faded; pseudo state chips are violet/pink. Design values get a unit button (length properties) and a color palette button (color properties) in place of a variable button on every field. Design-value bolts stay disabled because style values are not resolved at render time until the dynamic data phase. Palette names are the variable `group`; applying a palette in Design System > Colors saves immediately. Themes have `allowModeSwitch` (default on).
- Container elements default to a flex column (`BASE_CSS`, `:where(...)` so it never outranks user styles). Picker hover previews live in the editor store (`stylePreview`) and are drawn on a copy of the tree sent to the canvas.
- Fonts (Phase 2): metadata in `ProjectSettings.fonts`, files in storage under `fonts/<projectId>/<fontId>/`, served by the app at `/fonts/...`; no `project_fonts` table (settings JSON versions and publishes with the project). Google Fonts come through the Fontsource API and jsDelivr behind a host allowlist, so no request goes to Google at build or run time. Uploads need the rights checkbox and are validated by magic bytes. Only `active` fonts produce `@font-face`. Open items are listed under Phase 2 in `phases.md`. Server actions now accept up to 30 MB bodies (`serverActions.bodySizeLimit`) for font uploads. Shared action helpers moved to `apps/editor/src/server/authorize.ts`.
- Themes (Phase 2): `ProjectSettings.themes` (`packages/schema/src/theme.ts`). The FIRST theme created is the default and applies to every page and template until a page forces another (Page Settings > Appearance > Theme, `PageSettings.themeId`, null = Auto) or another theme's conditions match. Resolution: forced, then matching conditions (priority, then specificity page > route, then name), then the default. Deleting the default promotes the next theme; a forced id that no longer exists falls back to Auto. Conditions are static only for now (page ids, route glob with `*`), a separate small model from the dynamic-data `Condition` in `condition.ts`; runtime conditions and `exclude` come with the dynamic data phase. A theme stores per-mode overrides of project variables only; element defaults, fonts and custom CSS are open. Output: `:root[data-nxt-theme="slug"][data-nxt-mode="m"]{--nxt-*}` after the base `:root` variables; the default mode also applies when no mode attribute is set. Built pages (preview, site) include a blocking script that sets theme and mode on `<html>` (saved choice in localStorage `nxt-mode`, then system preference if enabled, then default mode); the canvas sets the attributes from the editor. The top-bar moon/sun switch picks light or dark; a theme without that mode shows its default mode. Custom modes exist in the schema but have no UI yet (the switch becomes a menu then). The Themes tab sits in the Design System modal (list on the left, editor on the right), following the Variables and Classes tab patterns because no design exists.
- CSS frameworks (Phase 2): every theme owns an optional `framework` (variables with light/dark values, classes CSS, scale settings). New projects get a Main theme with the generated Main framework (its class CSS is generated at output time, not stored). Imported frameworks keep their sheet; variable-only `:root` rules become variables, dark root rules become dark values, mode selectors map to `data-nxt-mode`. Framework classes are scoped with `:where(:root[data-nxt-theme])` so builder styles always win. Framework variable names are stored un-prefixed (`--primary`) unlike project variables (`--nxt-*`). Chosen without owner input: scale model (minor ratio at the min screen, major at the max screen, Core Framework style), 2 MB import limit, theme-less projects see a "Create the Main theme" action.
- Design System save model (Phase 2): the modal is a draft. Edits go to the editor store (canvas shows them) and are written only by the modal Save; Discard restores a snapshot of project, doc, history and save status. Every settings mutator bumps `classesTick` so `saveNow` writes ProjectSettings. Cross-page server operations (class rename/delete, variable rename) are queued as `pendingOps` and run on Save before the page save.
- Colors (Phase 2): framework colors are variables whose value is a color; palettes are the variable `group`; each theme framework has `colorPrefix`, `colorGroups`, `colorOptions`. Shade variables and color utility classes are derived at output and not stored. Scales carry a `kind` (text, space, radius). Export writes a `nextomic:framework` comment for exact round trips.
- Classes and variables (Phase 2): `ProjectSettings.classMeta` (category, locked), `classCategories`, `variableCategories`. Fonts get a `favorite` flag; a font is the group of its faces (weight and style keys), and uploading to an existing family merges files.
- 2026-11-06 Design panel round 5: Design and Element tabs are single-open accordions (the open group tells the editor what is being edited, used by "Hide edit border while editing"); the editor remembers each element's last edited Design setting; Transform and Filters are their own groups with visual editors; the Element tab has General and Attributes (HTML attributes with a safe-name allow-list, `{{attr.NAME@ID}}` tokens); element names are unique per page; version history is one global switch plus a per-page switch and limit (the global default limit input is gone, the default stays 200).
- 2026-11-07 Element names may repeat (no uniqueness check). The only element-targeting tag is `{{attr @ cssID:attribute-name}}`. Style values accept dynamic tokens, resolved when the CSS is built.
- 2026-11-07 Phase 2: custom CSS files are `ProjectSettings.cssFiles` (ordered, enabled, global or per-page scope, minify on publish) and the output layer order is fonts, variables, theme, custom CSS files, classes, elements. Classes can be exported and imported as plain CSS (simple class rules only; existing classes are never overwritten).
- 2026-11-07 Phase 2: animations are plain JSON in `ProjectSettings.animations` (folders, timelines, tweens). One planner (`planAnimation`) feeds the runtime, the editor preview and the GSAP code view. `gsap` (with ScrollTrigger and SplitText, free in the package) is a dependency of `packages/runtime` and loads on demand. The editor preview runs inside the sandboxed canvas iframe, never in the builder process.
- 2026-11-07 Phase 2: Design tab gets an Animations group for ready-made CSS animations (`ElementNode.animation`), separate from the GSAP timeline editor. Side panels cap at 25% of the window. `ProjectSettings.showClock` shows a clock in the top bar.
- 2026-11-07 Phase 2: the published site serves theme CSS as a separate file per theme (`/theme-css/<projectId>/<slug>.css?v=<publishedAt>`, public, `immutable`, version in the query); fonts, variables, custom CSS and class CSS stay inline so cascade order is kept (fonts, variables, theme link, custom CSS, classes). Preview and canvas keep the theme inline.
- 2026-11-07 Phase 2: custom color modes are extra entries in `Theme.modes` (max 6, ids are unique slugs; `light` and `dark` are built in and cannot be removed). Removing a mode deletes its variable overrides. The top bar preview is a sun/moon switch for two modes and a menu for more (`ModePreview`); the preview mode is a mode id string.
- 2026-11-07 Phase 3: templates (header, footer, error-404) are rows in a `templates` table with their own settings (rules, priority, theme, status draft or published, header and footer choice for the 404, marking). Pages and templates both record `created_by`, `published_at` and `screenshot_at`. Rules (`packages/schema/src/rules.ts`) replace the planned condition list: fields by group, operators by kind, AND or OR groups that nest, dynamic tags in keys and values; they run on the server per request, and browser-only fields never match there. A page picks header and footer as auto, none or a template. Layout is composed on the element tree (`composePage`): skip link, header, `main#main-content`, footer. The 404 comes from the segment `not-found.tsx` (status 404) with `middleware.ts` passing the address; with no published 404 template a plain default shows. Categories and tags live in `ProjectSettings.taxonomy` as four separate lists. Screenshots are 480 by 300 WebP, one per item at a fixed storage key, private to project members, made in the browser with `html-to-image` (a builder dependency). Builder field borders are 1px.

Header templates have sticky settings (`sticky`); `composePage` writes them to `data-nxt-sticky` and `packages/runtime` `startStickyHeaders` runs them. The editor canvas shows the header and footer that apply around a page (read only). Page SEO and description fields accept dynamic tags; tags are filled in when the page metadata is built and a link that resolves to something other than http(s) or a path is dropped. `@internationalized/date` was added to the builder dependencies for the date and time picker.

Code boxes get a Format button using Prettier standalone (CSS, JavaScript, JSON), loaded on demand; `prettier` is now a builder dependency of the editor.

Tags are `{{app.<name>}}` and `{{const.<name>}}` (JSON paths with dots). Renaming a used variable rewrites its tags in every page and template (`renameStateTag`); type change and delete confirm with the list of places. Persistence lives in `packages/runtime/src/persisted-state.ts` (namespaced keys, type signature, logout clearing, 4 KB cookie and 1 MB total caps); the site starts using it when actions can change state (Phase 5).
